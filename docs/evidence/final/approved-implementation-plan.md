# Watt? — RALPLAN implementation plan

Date: 2026-09-20. Baseline: `b1d4c11`. Planner proposal, pending sequential Architect then Critic review; not consensus approval or execution authorization. Planning only; no product edits.

## RALPLAN-DR

**Principles:** preserve native menu-bar utility architecture; one frame = one independently verified story; shared state and components before variants; explicit unavailable/error states rather than false readings; rendered visual and interaction evidence before Done.

**Top decision drivers:** (1) complete traceability of the existing 69 frames; (2) reliable shared lifecycle/navigation rather than duplicated mock screens; (3) honest verification despite the CLT-only environment and unresolved production integrations.

**Option A — selected: foundation-first, then individually delivered vertical screen stories.** Keep the existing feature-first executable package, add a thin native app/test host for verification, centralize boundaries and deterministic fixtures, and deliver each frame with its own evidence. Pros: smallest coherent extension of existing code, testable states, durable independent goals, preserves native scenes. Cons: initial foundation cost; platform/backend decisions can block final sign-off; some routes cannot be fully verified until later target stories land.

**Option B — foundation-first, then family batches with individual story sign-offs.** Same native architecture and 69 goals, but build each whole feature family in an isolated branch and sign off frames independently before integration. Pros: fewer shared-file conflicts and efficient family-level design calibration. Cons: larger integration batches, delayed feedback, greater risk of treating one view's completion as all variants complete. Viable only with independent frame evidence; do not bulk-close stories. A is selected for smaller reviewable changes and early integration feedback.

Rejected: tab-based dashboard, one monolithic screen goal, web recreation, or replacing verification with compile-only checks.

#### Shared approval cancellation acceptance matrix — existing J1.4/J2.4/J3.1 variants, not new stories

**Ownership and persistence:** F03 `HelperService`/`HelperState` and onboarding state own serialized interest changes; F04 scene coordinators own presentation tokens; P02 owns registration/status reconciliation. An origin is onboarding or Settings, not a notification. Persist desired intent, per-origin withdrawn/failure state, onboarding checkpoint and the operation receipt needed to reconcile after restart; in-memory tokens never restore presentation authority across launch. Re-query OS/helper status on restart without reopening scenes or installing from a stale receipt. A failed persistence write is a visible retryable error, not acknowledged cancellation/retry success; revoke that origin's navigation eligibility immediately for safety and reconcile before retry. Concurrent cancel/retry/success events are serialized, with no duplicate registration under either order.

**Cancellation boundary:** Cancel withdraws only its origin. Operation-wide app cancellation occurs when the last interested origin withdraws (or authoritative terminal failure ends the wait), not when the first observer cancels or merely closes. No new cancel-all UI is proposed. While another origin remains interested, keep its operation identity, wait generation and desired-on unchanged. Ending the app wait does not assert cancellation of an OS request: retain the receipt and suppress automatic install/connect attempts while desired-off; an authoritative late status may update effective availability, never navigate. Retry first reconciles the existing registration/OS request: pending → rejoin; already approved → authenticated connection; terminal/absent → at most one new operation after absence/no-in-flight proof. Uncertain status stays visibly pending/retryable rather than registering again.

Run all cases with onboarding=A and Settings=B, **then swap A/B**, using injected clocks/status and isolated persistence; also test cancel-before-success and success-before-cancel ordering. The table's explicit destinations and dismissal rules override generic story navigation wording.
